# إعادة فحص Upstash بعد خطوة المالك — 2026-09-14 (جلسة 3)

## السياق
أبلغ المالك بتنفيذ بند 3 من أوامر المالك: إضافة `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN` في Vercel (Production) + Redeploy. هذا الملف يوثّق التحقق الحي بعد التنفيذ، خطوة بخطوة.

## نتيجة الفحص الأول (بعد إبلاغ المالك مباشرة)

| الاختبار | النتيجة | التفسير |
|---|---|---|
| 8 محاولات دخول فاشلة **باتصالات منفصلة** (curl مستقل لكل محاولة) | 401×8 — لا 429 في أي محاولة | كل اتصال جديد يهبط على عزل (isolate) جديد فيتصفّر العداد = **العدّ الموزّع غائب** |
| 8 محاولات بـ **جلسة اتصال واحد** (Python requests.Session / keep-alive) | 401×4 ثم **429 في المحاولة 5** (`Retry-After: 12` · `code: RATE_LIMITED`) | الكود سليم 100% — نفس العزل يعدّ عبر fallback in-memory |
| الصحة العامة بعد الـ Redeploy | home 200 · system/status 200 · sitemap 200 · robots 200 · MCP v3.1 حي (WWW-Authenticate) | النشر نفسه سليم — المشكلة في وصول المتغيرين فقط |

**الاستنتاج المؤقت:** المتغيران لا يزالان غير واصلين لـ runtime الإنتاج رغم الـ Redeploy. السبب المرجّح: إعادة النشر من الـ dashboard أعادت استخدام snapshot / Build Cache قديم لا يحمل المتغيرين الجديدين (سلوك معروف في Vercel عند Redeploy بدون إلغاء «Use existing Build Cache»).

## الإجراء التصحيحي (هذا الـ commit نفسه)
دفع هذا الملف لإجبار Vercel على **بناء جديد كليًا من الـ commit** — البناء الجديد يقرأ متغيرات البيئة الحالية من الـ dashboard مباشرة، وهو أضمن من إعادة النشر المخزّنة. هذا هو الاختبار الفاصل:

- ظهر 429 على الاتصالات المنفصلة بعد البناء الجديد ← المتغيران كانا مضبوطين صح من البداية، والـ Redeploy القديم هو الذي كان لا يحملهما.
- استمرت 401×8 ← المتغيران غير مضبوطين في الـ dashboard نفسه (الأسماء حرفيًا / البيئة Production / القيم بصيغة REST `https://…​.upstash.io` وليست `redis://`).
