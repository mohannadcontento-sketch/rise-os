## 2. قياسات حية على الإنتاج (2026-09-14)

| المسار | TTFB التقريبي | ملاحظات |
|---|---|---|
| `/` (الرئيسية العامة) | ~120-200ms | HTML مُصدَّر ثابت + middleware رؤوس فقط |
| `/pricing` · `/features` · الصفحات القانونية | ~60-150ms | Server Components خالصة |
| `/sitemap.xml` · `/robots.txt` | ~40-120ms | مولدة ديناميكيًا خفيفًا |
| `/api/rise/ads` (بوابة الخطة) | ~200-350ms | استعلام خطة + كاش 10 دقائق للإعدادات |

- رؤوس الصدقونة: `Cache-Control: no-cache, no-store` على الـAPI فقط؛ الأصول الثابتة عبر `_next/static` (hashed immutable).
- HTTPS/TLS 1.3 + HSTS preload (راجع SECURITY_PRIVACY.md).
- ضغط Brotli/gzip فعال تلقائيًا على Vercel.

## 4. المتبقي على المالك (خارج الكود)

- ✅ **Upstash (الخطة المجانية) — مكتمل ومتحقق منه حيًا 2026-09-14 (جلسة 3):** بعد إضافة المالك للمتغيرين في Vercel وبناء جديد، أثبت الفحص ثلاثي المراحل العدّ الموزّع الفعلي:
  1. **جلسة واحدة (IP واحد):** 401×5 ثم **429 في المحاولة 6** مع رؤوس `X-RateLimit-Limit: 5` · `X-RateLimit-Remaining: 0` · `Retry-After: 22`.
  2. **فحص قاعدة Upstash مباشرة:** مفاتيح `@upstash/ratelimit:ratelimit:{IP}:/api/auth/login:{bucket}` تُكتب فعليًا مع TTL — المسار داخل الـ middleware هو Redis حصرًا (in-memory يتخطى عند وجود Redis — سطر 382).
  3. **الدليل المطلق (عزل جديد كليًا):** جلسة جديدة باتصال جديد فور تجاوز الحد → **429 من أول محاولة** — العزل الجديد لا ذاكرة له، فالرفع لم يصدر إلا من العدّاد المشترك في Redis.
  - ملاحظة منهجية مهمة (دُوّنت للأمانة): اختبار «طلبات متفرقة» من بيئة اختبار واحدة **غير صالح** كدليل رفض لأن الـ egress IP يتبدّل بين الاتصالات (3 IPs مختلفة من 8 طلبات) والعدّ لكل IP — التحقق الصحيح هو عبر جلسة موحّدة أو عبر فحص مفاتيح Redis مباشرة.
- مراقبة لوحات استهلاك Supabase/Upstash شهريًا (تذكير تقويم) — الخطة المجانية في Upstash: 10K أمر/يوم (كافية لحجم الإطلاق؛ راقبها عند النمو).
- (اختياري بعد الدخل) Sentry أو ما شابه لعمق أكوام الأخطاء — البنية الحالية (error_logs + status) تكفي للانطلاق.
