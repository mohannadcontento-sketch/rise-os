## 1. قرار المسارات: /login و /signup (البند الشرطي)

بند الخطة: «إضافة مسارات واضحة /login و /signup **إن لم تُثبت تجربة
query-mode الأفضل**، مع الحفاظ على backward compatibility».

**القرار المنفذ: المساران أُضيفا + وضع الاستعلام بقي — السطح واحد لا
مزدوج.** مكون بوابة الدخول (`login-page.tsx`) صار قابلاً للتهيئة عبر
`defaultMode` و`onLogin` الاختياري:

| المدخل | السلوك |
|---|---|
| `/app` بلا جلسة | البوابة داخل الصدفة (وضع الاستعلام) — **كما هو بلا تغيير** (توافق رجعي كامل) |
| `/login` | نفس المكون، تبويب الدخول نشط، بعد النجاح حملة كاملة إلى `/app` |
| `/signup` | تبويب الحساب الجديد نشط + الموافقة + مؤشر كلمة المرور |

- كلا المسارين `robots: noindex, nofollow` (صفحات المصادقة ليست محتوى
  قابلًا للفهرسة) + `metadata` عربية.
- الحملة الكاملة بعد الدخول (`window.location.assign('/app')`) **متعمدة**
  لا `router.push`: التطبيق يُقلع من الصفر فتلتقط مكونات الخادم الكوكيز
  httpOnly من أول عرض — بلا نافذة «جلسة شبه حية».
- روابط التحويل (CTA) في صفحة الهبوط: ٤ أزرار نية-التسجيل → `/signup`؛
  رابط «التطبيق» في التذييل → `/app` كما كان.
- الروابط العميقة القائمة محفوظة: `?forgot=1` و`?authError=` تعمل من
  أي مدخل (الرسائل الإلكترونية/الاستعادة غير متأثرة).
- قرار UX_FOUNDATION §1.2 (تأجيل قرار المسارات لهذه المرحلة) **حُسم**:
  كلا النمطين يعيشان معًا بلا تكرار كود — وهذا يخدم «رسميين وقابلين
  للتدقيق» (URL واضح قابل للمشاركة) و«الأفضلية المثبتة» معًا.

## 2. جدول user_consents (هجرة 038) — السجل القانوني

```sql
user_consents(id, user_id→auth.users ON DELETE CASCADE,
              consent_type ∈ {terms, privacy},
              policy_version, consented_at, metadata jsonb)
UNIQUE(user_id, consent_type, policy_version)
RLS: select-own + insert-own — لا update/delete من العميل إطلاقًا
```

- **الإدراج خادميًا فقط** من بوابة signup (service role في الإنتاج /
  Prisma في dev) — يُسجَّل **لحظة القبول** حتى لو كان البريد غير مؤكد
  بعد (احتياج قانوني: وقت الموافقة هو وقت النقر).
- `metadata`: بصمات دنيا `uaHash`/`ipHash` (SHA-256 مقطوعة ١٦ محرفًا) —
  قابلية تدقيق بلا PII خام.
- إعادة قبول نفس النسخة **لا تستبدل التاريخ الأصلي** (ignoreDuplicates
  / تجاهل P2002) — أول قبول هو السجل القانوني.
- القراءة عبر `GET /api/auth/consents` (بياناتي + مقارنة بالنسخ السارية
  + `currentVersionsAccepted`) — تدهور رشيق `notReady` قبل تطبيق 038
  (نمط feedback/037 نفسه).
- نموذج Prisma `UserConsent` + هجرة محلية (SQLite) — الاختبارات المحلية
  تمر بالمسار الحقيقي نفسه.

## 3. بوابة الرفض الخادمية (دفاع عميق)

```
POST /api/auth/signup
  ├─ بلا acceptedTerms=true        → 403 CONSENT_REQUIRED (رسالة عربية)
  ├─ policyVersions ≠ السارية      → 409 POLICY_VERSION_MISMATCH
  │     (يعيد requiredPolicyVersions ليصحح العميل روابطه)
  ├─ كلمة مرور ضعيفة (٨+/حرف/رقم)  → 400 (Zod — عقد جديد)
  └─ ناجح → إنشاء الحساب + سطرا consent + جلسة/تأكيد بريد
```

- **مصدر النسخ واحد**: `REQUIRED_POLICY_VERSIONS` مشتق من
  `LEGAL_LAST_UPDATED` (site.ts) — نفس المرجع المعروض في /terms و
  /privacy («مرجع النسخة»). تحديث النصوص القانونية مستقبلًا = إصدار
  موافقة جديد مطلوب تلقائيًا في كل تسجيل جديد — **آلية نسخ حية لا
  إعداد يدوي**.
- العميل يرسل النسختين التي رآهما؛ الاختلاف يعني صفحة قانونية مخبأة
  قديمة → 409 → العميل يحدّث النسخ ويعرض طلب قبول جديد (checkbox
  يُفرغ + رسالة راجع-واقبل).
- تُطبق نفس القوة على الوضع المحلي (mock) والسحابي.

## 4. واجهة التسجيل (UX)

- **checkbox الموافقة الإلزامي** بروابط واضحة: «الشروط» و«سياسة
  الخصوصية» تفتح في تاب جديد (`rel="noopener"`) + سطر «النسخة السارية»
  بأرقام شرقية من مصدرها الحي.
- **مؤشر متطلبات كلمة المرور** حي (يظهر عند أول محرف): ٨ محارف + حرف +
  رقم — علامات ✓ خضراء / ✕ محايدة، `role="status"` + `aria-describedby`
  يربط الحقل بالمؤشر (a11y). الزر مقيد حتى استيفاء الثلاثة + الموافقة.
- **بطاقة تأكيد البريد كمعلومة** (بنفسجي هادئ — ليست خطأ أحمر): بعد
  `needsConfirmation` أو `email_not_confirmed` — زر إعادة إرسال **بعدّاد
  تهدئة ٣٠ ثانية** + اختصار «وصلتك الرسالة؟ سجّل دخولك».
- زر إظهار/إخفاء كلمة المرور بـ aria-label عربي (كما كان) + كل النصوص
  فصحى مبسطة بلا لغة لوم (§7).

## 5. حالات البريد (بند «معالجة email confirmation/resend/reset-password»)

| الحالة | السلوك | قبل المرحلة |
|---|---|---|
| تسجيل بلا تأكيد | بطاقة معلومات + إعادة إرسال + تهدئة | كانت رسالة خطأ حمراء |
| دخال ببريد غير مؤكد | خطأ + زر إعادة إرسال (بالتهدئة الآن) | كان بلا تهدئة |
| رابط استعادة منتهي | `?forgot=1` → وضع الاستعادة + إرشاد | كان (محفوظ) |
| reset-password | صفحة مستقلة بحالاتها (محفوظة — QA-14) | كان |

## 6. تدقيق التخزين (بند «تأكيد عدم وضع session/token في localStorage»)

جرد كامل لمواقع الكتابة في تخزين العميل (النتيجة في
`docs/phase-12/SECURITY_PRIVACY.md` — قسم المرحلة 20): **صفر توكن في
أي تخزين عميلي**. `rise-user-info` = بيانات واجهة غير حاكمة فقط؛
المفاتيح القديمة (`rise-auth`, `sb-*-auth-token`) **تُمسح** ولا تُكتب.
الكوكيز `rise-access`/`rise-refresh` httpOnly+SameSite=Lax (مقيس
بالاختبار من رؤوس الاستجابة مباشرة + `document.cookie` لا يكشفها).

## 10. أسرار التشخيص (للسجل)

1. **تعبئة ما قبل الترطيب تُمسح** (dev/turbopack): الحقول تُملأ قبل
   اكتمال hydration فتبقى القيمة في DOM بلا حالة React → الزر معطل
   بلا رسالة. العلاج الموحد: `waitForLoadState('networkidle')` قبل كل
   تعبئة نموذج بعد goto — مطبق في auth.spec وlogin.spec.
2. **رسالة Zod الافتراضية الإنجليزية تسبق الـrefine**: غياب
   `acceptedTerms` يفشل فحص النوع (`boolean/undefined`) قبل وصول
   الرسالة العربية → الرسالة الموحدة صارت في المتصل لا في المخطط.
3. **`SameSite=lax` بأحرف صغيرة**: الطبقة السفلية يطبّع القيمة —
   المقارنة صارت غير حساسة للحالة.
4. **بوابة الأدمن ترد 403 قبل فحص الجلسة** («أدمن فقط») — عقد مقيس
   بالـcurl؛ التوقعات صُححت لتطابق الواقع لا العكس.
5. **حدّ signup ٣/دقيقة**: التشغيلات المتكررة خلال نافذة واحدة تظهر
   فشلًا كاذبًا — الانتظار ٦٥ ث قبل كل جولة (نمط home.spec المتبع).
